## P0 · 手机号泄露收口（已force-push）

**结论**：号码不在任何历史 `.py` 源码里（那些位置早就是 `+86XXXX`），唯一载体是
一个被入库的 `.pyc`：`deva/naja/tasks/__pycache__/ai_daily_report.cpython-314.pyc`
（`ec6544cf` 2026-04-13 加入，`a7cf64a0` 2026-04-17 删除）。它可达 master /
origin/master / 两个 trae 分支，覆盖 404 个提交 + tag `v1.8.0`。

**做法**：`git clone --mirror` → `git filter-repo --invert-paths --path-glob '*__pycache__*'`
→ 校验（号码 0 命中、`__pycache__` 路径 0、tip tree 不变）→ force-push master + tags
→ 删 `develop` / 3 个 `trae/*` 远端分支 → 本地 `update-ref` 对齐。

**取证方式**（以后复用）：`git cat-file --batch-all-objects --batch` 直接 `\n`
全量喂进去再读输出会**死锁**（管道缓冲写满）。改用 `git grep -f <pattern文件>
$(git rev-list --all)` 一次进程扫完全部提交。

**残留**：
- 本地仍有两个 `refs/codex/turn-diffs/checkpoints/*`（tree 引用）带着号码，从未推过远端。
- GitHub 缓存视图要人工提 support。
- 4 个 fork 都是 2019–2021 的，早于这段历史，基本不受影响。

**误报澄清**：`526d6ed` 移走的「持仓」只是账户名 + `0.0` 占位的标的，没有真实股数；
`state/system/state.json`（历史唯一入库过的运行态文件）里也没有持仓。不需要为持仓做二次清理。

## P1 · 分类器改吃季频（已提交）

`repricing_service._classify()` 原来吃年度 4 期。改吃 `fundamental.points` 的季度
TTM 序列（实测 30~35 期）。顺带挖出三个「有财报的票变成没数据」的坑：

1. `us_series` 取标签「第一个非空就用」→ AMD 的 `Revenues` 只有 4 行早年数据，
   近几期营收/TTM 全 None，毛利率整只票消失。改为取「覆盖最新期、样本最多」。
2. 毛利率只认 `GrossProfit` → AMZN 只有 2009 年几行。改用 Revenue − Cost 反推，
   按「最后一期谁更新」择优（反推必须带 `start`，否则 `_rolling_sum` KeyError）。
3. `us_series` 抓取失败返回 `[]`，与「这家没财报」无法区分 → 抛 `SecFetchError`，
   服务层新增 `series_with_status()` 给三态。

**如实记录**：AMD 仍是 cyclical（不是 bug，它的季度 log 标准差 5.04、43% 季度负增长）。
计划里「换季频就能修正 AMD/TSLA」只对 TSLA 成立（→ base，不再乱猜）。
真正修好的是**数据完整度**与样本充足度（0.5 → 1.0），不是结论方向。

## 经验

- `git cat-file --batch` 直接 `\n` 全量喂 stdin 再读 stdout 会死锁（管道缓冲写满）；
  改成 `git cat-file --batch-all-objects --batch > 文件` 再扫文件。
- 历史重写后「本地还留着旧对象」最常见的原因是**没跟着更新的 tag**，不是 reflog。
