# 首页「数据源 / 策略」统一口径 —— 评估与方案

> 生成时间：2026-10-20
> 触发问题：首页数据源卡显示的是数据源系统里固有策略的值，但全系统还有很多地方在获取外部数据、还有很多策略在跑，没有汇总进来。

---

## 一、结论（先说答案）

**不要在首页 UI 里补特例。** 首页只是渲染层，问题的根因是「系统里有三套互不知情的运行清单」，
UI 无论怎么补都不可能补全 —— 下次新增一个取数点，没人会记得回来改首页。

正确做法是新增一层 **统一清单层（Fleet Registry）**：把「系统里有什么在跑、什么在取外部数据」
变成**可枚举的一等事实**，首页只负责把它渲染出来。并配一个**完整性守卫**，让「新增取数点忘了登记」
变成守卫失败，而不是静默丢失。

2. **汇入代码是一条永远失败的 import**（已实测）：
   ```python
   # deva/naja/market_hotspot/strategies/strategy_manager.py:800
   def _auto_register_to_strategy_manager(manager):
       try:
           from deva.naja.strategy import get_hotspot_manager as get_sm   # ← 这个名字不存在
   ```

## 三、根因：三套互不知情的清单

```
① DatasourceManager   deva/naja/datasource/manager.py    yaml 驱动，5 个   ← 首页唯一在看的
② StrategyManager     deva/naja/strategy/manager.py       yaml 驱动，17 个  ← 首页唯一在看的
③ HotspotStrategyMgr  market_hotspot/strategies/...       代码驱动，14+ 个  ← 汇入失败，看不见
④ 散落取数器 / 常驻 runner（下文表）                       无清单           ← 完全黑盒
```

`home/ui/__init__.py` 只拉了 ①②：
```python
ds_stats       = ds_mgr.get_stats()        # 只有 5 个
strategy_stats = strategy_mgr.get_stats()  # 只有 17 个
```

## 五、方案设计（三层）

### 第 1 层 —— 登记册（事实层，infra）
新文件：`deva/naja/infra/observability/fleet_registry.py`

```python
@dataclass
class UnitCard:
    unit_id: str              # 唯一 ID
    kind: str                 # "datasource" | "strategy"
    name: str                 # 人读名
    source: str               # 来自哪个体系：datasource_mgr / strategy_mgr / hotspot / probe / manifest
    state: str                # running | stopped | unknown | skipped   ← 四态，不许合并
    last_success_ts: float    # 0 = 从未成功
    last_error_ts: float      # 0 = 从未失败
    error_count: int          # 累计（只作参考，不作当前故障判据）
    output_count: int         # 累计产出
    cadence: str              # 期望节拍，如 "5s" / "cron 0 9 * * *" / "按需"
    note: str                 # 取不到/不适用时写原因
```

- 只存**事实**，不存判断。陈旧度在**读取时**算（沿用既有规则）。
- 提供 `declare()` / `snapshot()` / `by_kind()`。

### 第 2 层 —— 适配器（把四类来源汇进来）

| 来源 | 适配器 | 难度 |
|---|---|---|
| DatasourceManager | 直读 `list_all()` + `_state`（已有 `error_count` / `last_error_ts`） | 低 |
| StrategyManager | 直读 `list_all()` + `_state` | 低 |
| HotspotStrategyManager | **先修 ImportError**，再直读 `strategies` | 低（1 行） |
| 散落取数器 / 常驻 runner | **探针装饰器** + **声明式清单兜底** | 中 |

**探针（主）**：在真正的取数函数上挂 `@probe(kind="datasource", name="新浪A股行情", cadence="5s")`，
每次调用自动记 `last_success_ts` / `last_error_ts` / 计数。
→ 这是**唯一能保证「新增取数点自动被看见」**的机制：漏登记的代价从「默默不见」变成「漏个装饰器」，
而漏装饰器会被守卫扫出来。

**声明式清单（兜底）**：一时改不动的代码，在清单里显式登记 `unit_id / 取什么 / 状态读取 callable / 节拍`，
并必须写 `note` 说明为什么不用探针。

### 第 3 层 —— 首页渲染
- **数据源卡**：主数字 `运行中 N / 共 M`；副行给**最陈旧的取数点名字 + 时长**；
  判读行 `⚠ 新浪A股行情已 6 小时未成功`。
- **策略卡**：主数字 `运行中 N / 共 M`；副行产出；判读行给未运行清单。
- **卡片下方可展开「全量清单」面板**：按 kind 分组的表格（名称 / 来源 / 状态 / 最近成功 / 最近失败 / 节拍）。
  首页空间有限，卡上只放结论，明细放展开区。

## 六、必须写进模块 docstring 的规则（防静默失效）

1. **四态不许合并**：`unknown`（没探针、读不到）≠ `stopped`（确实停了）≠ `error` ≠ `skipped`（按设计不该跑）。
   `unknown` 首页显示灰 + 原因，**绝不当 0**。
2. **取不到就写原因**，不写 0。
3. **累计计数 ≠ 当前故障**：`error_count` 只作参考，判据用 `last_error_ts` 的新鲜度。
4. **陈旧度读取时算**，不存「是否健康」这个结论。
5. **禁止 `except: pass` 吞掉登记失败** —— 本次事故的直接成因。登记失败必须写 warning 日志 + 落一条 `state="unknown"` 的卡。

## 七、守卫（关键闭环）

新增 `scripts/verify/verify_fleet_registry_completeness.py`：
- 扫全仓 `requests / httpx / aiohttp / urllib / websocket` 的对外调用点，
- 断言每个都已在 registry 登记，**或**显式列入 allowlist 并在 `note` 写明原因；
- 否则守卫失败。

守卫还要按本仓既有方法论做**负向注入**：
- 故意让一个已登记单元的状态读取抛异常 → 断言它变成 `unknown` 且带原因，而不是消失或变成 0；
- 故意删掉一个登记 → 断言守卫报缺失。
- ❗读被测模块必须用 `spec_from_file_location` 重加载，不能 `import`（否则拿到 `sys.modules` 旧对象，全绿但没守）。

## 九、实施结果（2026-10-20 21:10 完成，Naja 已重启）

### P0 —— 修好热点策略汇入（实测生效）
| 项 | 改前 | 改后 |
|---|---|---|
| 首页/策略 API 总数 | 17 | **31**（17 声明式 + 14 热点） |
| 运行中 | 1 | **14** |

- 修正 `get_hotspot_manager` → `get_strategy_manager`；`except: pass` → `log.warning`。
- `StrategyManager` 新增 `attach_external_entry()`，外部条目进**独立 `_external_items`**
  （`load_prefer_files()` 会 `clear()`，混在 `_items` 里一重载就被抹）；
  `list_all()` 按 id 合并去重，`_items` 优先。
- 顺手修 `get_daily_review_scheduler()`：原来**每次调用 new 一个新对象**（还 import 了 SR
  却没用），首页必然读到假「已停止」。

### P1 —— 统一登记册
新增 `deva/naja/infra/observability/fleet_registry.py`：`UnitCard` 四态、
只存事实不存判断、陈旧度读取时算；三个适配器 + 常驻 runner 清单。
⚠️ runner 一律走**模块级 getter** 而非 `SR()`：container 用 `get_xxx_runner()` 启动，
而 register.py 表里另有同名单例（工厂 `Class()`），SR() 会造出第二个从未 start 的实例 → 假「已停止」。

首页两张卡改读登记册，并新增可展开的「全量清单」面板（`home/ui/fleet.py`）。

### P2 —— 探针 + 守卫
- 15 个取数模块挂 `@probe(...)`（新浪行情总线 / 美股 / 热点实盘 / 全球期货 / 富途 /
  FRED / SEC / 东财 / IMA / 金十新闻 / 文章监控 / arXiv / HF / GitHub / 叙事指数 / 时点基本面）。
- `scripts/verify/verify_fleet_registry_completeness.py`：扫 23 个含网络库 import 的模块
  → 13 已登记、10 在白名单（均写明原因）；扫描下限 15 防正则失效假绿；
  四态守恒 / unknown 必带原因 / 适配器失败留痕 / 热点不重复计数。**负向注入 4/4 捕获。**
- `verify_home_stats_cards.py` 同步新口径，注入增至 **5/5 捕获**。
- 全量守卫 **99 份通过 / 0 失败 / 1 跳过**。

### 顺手修掉的守卫自伤
两个富途守卫用**桩件包**替代 deva，新加的 `deva.naja.infra...` 导入没桩 → 连被测模块都加载不了。
已补桩（`KIND_DATASOURCE` + `probe` 空装饰器）。
